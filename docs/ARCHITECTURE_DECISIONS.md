# 架构决策记录（ARCHITECTURE DECISIONS）

> 记录项目关键架构决策及其理由，供后续开发与评审回溯。

---

## ADR-001：技术路线从「深度搜索」转向「轻量网络 + 短搜索」

- **背景**：实测 Alpha-Beta 搜索在部分局面需数分钟完成一次决策，不适合交互式本地部署。
- **决策**：最终产品核心是「本地 GPU 运行、推理快、模型轻量、棋力较强」的 AI Agent；采用轻量 Policy-Value 网络为主，必要时触发短时战术搜索。
- **理由**：搜索深度无法弥补手工评估函数的短板；神经网络评估是突破棋力天花板的正确方向，但需轻量化以保证本地部署。
- **影响**：Phase 4 的 CNN/ResNet 从「辅助搜索」提升为「部署核心」。

---

## ADR-002：训练与部署分离

- **决策**：训练阶段允许搜索引擎/MCTS/教师模型/批量 GPU 推理/自对弈/蒸馏；部署阶段只用轻量网络 + 少量战术检查 + 短搜索。
- **理由**：训练可以慢、部署必须快，二者约束不同，应解耦。

## ADR-003：棋盘用 Python list 而非 numpy（暂不替换）

- **背景**：视频建议 numpy 连续内存更快，任务书要求"不要盲目替换正确且高效的数据结构"。
- **决策**：当前 `Board` 用二维 `list`，`make_move`/`get`/`undo_move` 均为 O(1)，实测 1 万次 make/undo 仅 3.8ms（0.38μs/次），非瓶颈。
- **理由**：替换 numpy 会牵动 environment/engine/agents 全部模块，风险大、收益小。
- **状态**：**暂不替换**；若未来神经网络输入需要，仅在 `State.encode()` 层转换（已支持 `board_array()`）。

## ADR-004：胜负判断增量化（已实现）

- **决策**：`check_win_at` 只检查新落子的横/竖/两条对角线，O(win_length)。
- **理由**：五子棋胜负必由最新一手决定，无需全盘扫描。
- **状态**：已实现（`environment/rules.py`），与视频建议一致。

---

## ADR-005：平局判断用计数器（本轮完成）

- **决策**：`Game.play` 用 `move_count >= size*size` 判断平局，替代 `board.is_full()` 全盘扫描。
- **理由**：O(1) vs O(N²)，虽单局收益小，但为未来大规模自对弈累积收益。
- **状态**：本轮已实现。

---

## ADR-006：VCF 独立节点预算（本轮完成）

- **决策**：`VCFSearcher` 增加 `max_nodes`（默认 20000）节点预算，配合已有时间预算，双重防止无限递归/全盘扫描爆炸。
- **理由**：VCF 的 `_find_rush_four_points` 等函数存在全盘扫描，深递归下可能指数级爆炸，单靠时间预算（200ms）粒度不足。
- **状态**：本轮已实现。

---

## ADR-007：搜索统计埋点（本轮完成）

- **决策**：`SearchStats` 扩展 `candidate_count / vcf_calls / vcf_nodes / tt_hits / tt_probes / leaf_eval_count / leaf_eval_time_ms / max_recursion_depth / timed_out` 等诊断字段，提供 `summary()` 一行摘要。
- **理由**：定位耗时来源（诊断结论见下）。
- **状态**：本轮已实现。

### 本轮诊断结论（Task 2）

在 depth=4、8 候选、带 VCF 配置下：
- 开局(1手)：346 节点 / 94.6ms / NPS 3658
- 中盘(12手)：581 节点 / 279ms / NPS 2082

**耗时主要来源**：
1. **叶节点估值**（`evaluate_board` 全盘棋形扫描）占总耗时 25–30%；
2. **TT 命中率偏低**（5–9%），置换表价值未充分发挥；
3. VCF 节点数少（2–6），**不是瓶颈**。

## ADR-008：批量推理接口协议（本轮设计）

- **决策**：定义统一的模型推理协议（见 `docs/MODEL_INTERFACE.md`），但不建立空类/空框架。
- **理由**：为未来 Policy-Value 网络预留接口，避免过度抽象。
